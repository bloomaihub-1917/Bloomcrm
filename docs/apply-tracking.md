# 신청서 접수 이력

전시 → 기업 드로어 → **신청항목** 탭. 신청서를 몇 번 받았고, 그때마다 무엇이
달라졌는지를 남긴다.

## 왜 만들었나

접수일을 담는 칸이 하나(`exhibitors.app_received_at`)뿐이었다. 그런데 기업은
신청서를 한 번만 보내지 않는다.

- 프로그램북 소개글을 고쳐 다시 보내고
- 전시패스를 더 달라고 **메일 본문**으로 알려 오고
- 의자를 빼달라고 **전화**한다

칸이 하나라 덮어쓰면 최초 접수일이 사라지고, 안 고치면 변경이 안 남는다.
실제로 변경 이력이 품목 비고에 손으로 적혀 있었다 — `"2026-08-25 추가 신청"`.
사람이 안 적으면 안 남고, **무엇이 바뀌었는지(수량 1→2)는 적을 데조차 없었다.**

## 접수를 줄로 쌓는다

`exhibitor_apps` — 한 번 받을 때마다 한 줄.

```
seq          1, 2, 3 …
received_at  받은 날
channel      신청서 | 메일 | 유선 | 현장
kind         최초 | 변경 | 취소
reason       왜 다시 받았나 (프북 수정 · 전시패스 추가 …)
file_name    원드라이브 파일명 (파일로 왔을 때만)
handled_at   반영 완료 — 비어 있으면 "아직 반영 중"
summary      무엇이 달라졌나 (닫을 때 자동으로 만든다)
```

**경로가 달라도 접수는 접수다.** 파일 없이 전화로 받은 변경도 같은 표에 한 줄로
들어가야 "8/28 통화로 의자 2개 추가"가 근거로 남는다. 최초 접수는 기존
`app_received_at`도 함께 채운다 — 체크리스트가 보는 칸과 갈라지지 않게.

## 추가인지 변경인지 사람이 고르지 않는다

이게 핵심이다. 매번 "이건 추가인가 변경인가"를 사람이 판단해 고르게 하면
**안 적히거나 틀리게 적힌다.** 지금 품목 비고가 그 증거다.

대신 접수 건을 **반영 중**으로 열어 두면, 그동안 고친 품목이 자동으로 그 건에
달린다.

```
exhibitor_items += app_id        어느 접수 건으로 들어왔나
                += change_kind   추가 | 변경 | 취소
                += prev_qty / prev_amount   바뀌기 전 값
                += voided_at     취소된 줄
```

품목을 새로 넣으면 `추가`, 수량·금액을 고치면 `변경`(바뀌기 전 값을 한 번만
붙잡는다 — 같은 건 안에서 두 번 고쳐도 "1 → 3"이 나와야 한다), 취소 버튼을
누르면 `취소`. 반영 완료를 누르면 요약이 만들어진다.

```
2차 접수 · 2026-08-28 · 유선 · 의자 추가 요청
  + C-040 접이식 체어 2개 추가
  ~ T-013 라운드 테이블 1 → 2
  − 인포데스크 랩핑 1개 취소
```

무엇이 달라졌는지는 **데이터가 이미 알고 있다.** 사람은 "받았다"와 "다 반영했다"만
누른다.

## 취소는 지우지 않는다

`voided_at`으로 내린다. 진짜로 지우면 이미 나간 인보이스가 왜 그 금액이었는지
설명할 수 없다.

- **발주·정산·대장에서는 빠진다** — `liveItemsFor()`를 쓰는 곳 전부
- **목록에는 취소선으로 남는다** — 왜 빠졌는지 그 자리에서 확인해야 한다
- 잘못 넣은 줄은 `✕`로 진짜 삭제한다. 둘은 다른 동작이다

## 인보이스 발행 뒤에 바뀌면 알린다

신청이 바뀌면 청구액도 바뀌는데 인보이스는 이미 나가 있다. 놓치면 받을 돈과
청구한 돈이 갈린 채로 행사가 끝난다.

마지막 유효 인보이스보다 늦게 받은 변경 접수가 있으면 정산 탭 위에 경고가 뜬다
(`needsReissue`). 옛 인보이스를 무효로 두고 다시 발행하면 된다.

## 폴더가 곧 접수 기록이다

신청서는 원드라이브 한 폴더에 모여 있다. 같은 기업 파일이 둘이면 두 번 받은
것이고, 파일명 꼬리에 왜 다시 받았는지가 적혀 있다.

```
2026_KIC_Application_Form_Novotech_updated Aug 14.docx
2026_KIC_Application_Form_Novotech_updated Aug 28.docx     ← 2차
2026_KIC_Application_Form_씨엔알리서치_가족사 소개 포함.docx  ← 2차
```

```bash
node db/import-apply-files.js --dry
```

파일 53개에서 접수 54건을 만든다(공동 부스 파일 하나가 두 기업이라 하나 더).
파일은 CRM에 올리지 않고 파일명만 남긴다 — 원본은 원드라이브에 둔다(로고·그래픽
폴더를 훑던 방식과 같다). 여러 번 돌려도 이미 들어간 파일명은 건너뛴다.

파일명이 제각각이라 이름 매칭에 손이 간다.

- 공통 접두어(`2026_KIC_Application_Form`)를 **날짜보다 먼저** 벗긴다. 날짜부터
  지우면 `2026_`이 사라져 접두어가 더는 안 잡힌다
- `_EN_`의 `EN`은 `\b`로 못 뗀다 — 밑줄도 단어 문자다. 알파벳만 경계로 본다
- 한글 이름은 두 글자짜리가 실제로 있다(`㈜심유` → "심유")
- 이름이 그대로 맞는 곳을 먼저 쓴다. 품고 있는지만 보면 `labcorp`가 5곳에 걸린다
- 그래도 안 되는 것은 `SPLIT`에 사람이 적는다 — 파일명 오타(`HLB 바이오스템` vs
  `HLB바이오스텝`), 옛 사명, 한 파일에 두 기업(공동 부스)

**폴더에 없는 접수는 이 스크립트가 만들 수 없다.** 메일 본문·유선으로 온 변경은
흔적이 없다. 그건 화면에서 사람이 한 줄 추가한다 — 스크립트는 손입력을 줄이는
쪽으로만 쓴다.

## 자유 메모는 그대로 둔다

`extra_equipment`("신청 내역 — 받은 그대로")는 건드리지 않았다. 꼭 알아야 하는
메모라 품목과 별개로 남긴다.
